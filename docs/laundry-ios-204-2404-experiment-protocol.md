# 洗衣 iOS 204/2404：诊断对照协议

日期：2026-10-02。本轮目标是收集资源选择、访问时序和错误行为的证据；尚未解决 AppKey 空值与统一签名初始化失败。

## 已修正的观察问题

- 缺图观察以前没有校验哨兵的实际命中。现在必须确认 fopen/open 各一次，文件身份及内容各一致两次；创建或自检失败即关闭观察，并清理哨兵。
- 阶段行以前输出累计数。现在输出相邻边界之间的增量，窗口文件行标明开始与结束边界；全窗口总数仍单独保留。
- 沙盒采样自身的读取以前可能混入 SDK 统计。现在仅暂停采样线程，SDK 工作线程继续观察；暂停支持嵌套并在 finally 恢复。
- 目录范围以前会接纳相同前缀的兄弟目录和任意相对文件名。现在只有带目录分隔符的绝对路径前缀匹配才计入目录内记录。相对路径不能由这一记录证明身份。
- 对照生成以前忽略写入失败。现在先校验完整来源，再写入并读回核对；失败不调用 SDK，并删除自己创建的目录。并发检查在创建目录之前拒绝。
- baseline 复制来源的 Info.plist、清单与两张原图，避免自行改造 Bundle 元数据。来源缺失、变体未知或完整性失败不能作为有效基线。
- 沙盒变化以前展示相对路径，并把变化称为派生缓存。现在只报告匿名标签、大小与有限扫描状态；内部摘要不进入报告，变化不归因于 SDK。

正式检查仍要求资源完整性通过；只有诊断入口在完整来源上派生缺图等变体，再使用对照目录调用 SDK。不会修改导入来源。

## 覆盖面的边界

宿主入口自检只证明自身的 fopen/open 跟踪可用，不能证明完整覆盖 SDK、系统库或初始化前的访问。当前静态分析找到的 Foundation 读取用于 embedded.mobileprovision 与 init.config/update.config；ZIP 打开回调另属 C 文件入口。没有建立这些调用到安全图片的读取链路。

跟踪只统计符合条件的读入口。一次打开、身份一致或观察器计算出摘要，均不能单独证明 SDK 随后读取或解析了文件内容。

目录内记录最多 48 条，不是完整文件清单；条目代表打开事件，重复打开会重复记录。除固定资源与配置名外，文件名以匿名标签展示。

沙盒每次最多访问 600 个目录条目、采集 64 个常规文件，每个内容摘要最多读取 64 KiB。大文件只比较大小；没有变化不排除未覆盖文件、同大小内容变化或内存缓存。新进程不会清除持久磁盘状态。

## 变体与允许的解释

每个变体必须使用新的应用进程。检查页选择后锁定本进程；诊断目录运行完成后清理。

| 变体 | 改变的内容 | 可以提供的证据 | 不能直接证明 |
| --- | --- | --- | --- |
| baseline | 原图与 Bundle 元数据保持一致 | 是否复现当前错误 | 根因、SDK 已消费文件 |
| both-missing | 对照目录不写两图 | 结果是否对两图存在性敏感 | 原图已被读取、故障位于解析层 |
| main-missing | 不写主图 | 对主图存在性的敏感性 | 主图与另一张图的读取顺序 |
| mwua-missing | 不写 mwua 图 | 对该图存在性的敏感性 | 具体解析器或失败分支 |
| main-zero | 主图同长度全零 | 与原图的行为差异 | SDK 格式代际、具体校验算法 |
| main-header-only | 保留前 16 字节，其余置零 | 对这组字节变化的敏感性 | 前 16 字节就是安全图片格式头部 |
| main-truncated | 主图截断一半 | 对长度和内容同时变化的敏感性 | 仅有长度校验导致错误 |
| main-random | 主图同长度随机内容 | 对另一组内容变化的敏感性 | 具体字段含义或权限问题 |

仅缺图就改变错误码，可能来自存在性检查、选路、初始化条件或实际读取；没有访问链路证据时，不能直接写成“读到成立”。内容变化导致错误变化，也不能单独确定解析层级。

AppKey 的 204 与统一签名的 2404 属于不同接口，分别比较其阶段结果，不以数字相似推定同一根因。未经核对的错误码保留数值，不直接套用另一版本或另一平台的定义。

## 静态取证：错误码不是注册表 miss，而是解析器真读了图（本轮）

`tools/audit_sg_appkey_dispatch.py` 对本地 `build/laundry-ios-analysis` 的 IR 复核，得到一条可排除性证据：

- 原生函数表查找 `CMa02p9LOLd8m1` 在 **miss（找不到处理器）时返回的是大数**：`(group*10000+middle*100+sub)*10000 + 9904/9905/9906`。对 `(1,6,43,0)` 即 `106439904/106439905/106439906`。
- 但真机与两个包装层观测到的底层 `raw` 是 **3 和 4**（AppKey 侧 `4+200=204`；统一签名侧 `switch` 把 `3→2403`、`4→2404`）。
- `(1,6,43,0)` 与 `(1,6,8,0)` 在四个 framework 的原生注册表里都**没有处理器**，说明它们由 AVMP/uvm 字节码实现（虚拟化查询命中）。

**结论（静态证据支持）**：`raw=3/4` 不可能来自「函数表没找到」——miss 会给出 `1064399xx` 而非个位数。因此 `raw` 是 **AVMP 字节码解析器真正打开并校验了图片之后**返回的语义小码：`3`=没找到可用图片数据、`4`=找到但格式/解析失败。这与真机「缺主图→raw 3、主图存在但损坏→raw 4」一致，**证明主图确实被读取并进入了内容校验**，不是纯存在性检查，也不是选路错误。

这把根因从「多种可能」收敛到一条：**候选 5.6 SDK 的 AVMP 图片解析器读到了校园 6.8 图片、按自身格式校验后判为 `raw=4`**。仍属高置信推断，未定位到字节码内的具体校验指令（静态不可见），也未证明代际不兼容是唯一原因。

## 为什么必须换观察面：fopen/open 零命中是方法缺陷（本轮）

AVMP/uvm 宿主函数表（165 项）里**没有 `fopen/open/read/fread/stat`**，字节码读内容只能经 `objc_msgSend` 调 Foundation，探测路径用 `access/lstat/opendir/readdir`。app 级 `fopen/open` interposer 只覆盖自身命名空间、看不到 Foundation 内部读取。两者叠加使 fopen/open **必然零命中**，与 SDK 是否读文件无关。继续加 fopen/open hook 无意义。

## 宿主通道对照轮（下一轮设备验证）

本轮已在 `ProbeResourceTrace` 落地宿主通道观察（`CampusProbeTraceOptionsHostChannels`），诊断入口默认启用。它能区分的、与不能下的结论：

| 观察 | 能证明 | 不能证明 |
| --- | --- | --- |
| `NSData/NSString/NSFileManager` 通道对 `yw_1222*.jpg` 目标命中 >0 | 字节码确实经 Foundation 读了目标图片 | 读后如何解析、拒绝在哪一步 |
| 目标命中且「内容一致」计数 >0 | 读到的就是我们改的那份图 | 代际/字段语义 |
| `access/opendir` 命中对照目录 | 路径探测发生在该目录 | 内容是否被消费 |
| 全部宿主通道仍零命中 | 在已覆盖入口内未观察到 | SDK 没读文件（可能走未覆盖通道/内存预置表） |

设备步骤（每个变体一个新进程，沿用 §第一轮）：

1. 先跑 `baseline`：确认宿主通道自检通过（报告含「宿主通道说明」行且各通道自检命中），并复现 204/2404。
2. 再跑 `main-zero`（或 `main-random`）：对比宿主通道行——
   - **NSData/NSFileManager 目标命中 >0 且内容「不同」>0** → 直接坐实「解析器读到了被改坏的主图」，根因锁定在字节码解析层；下一步只剩「同代 SDK + 配套图片」这一条正路（见 rootcause 文档路线 A）。
   - **命中但内容「一致」** → 命中的是别的副本或缓存，回到路径/派生文件排查（对照 C：只在主 Bundle 放图）。
   - **全零** → 记录为「已覆盖入口内未观察到」，改查未覆盖通道（如 `mmap`、`NSFileHandle` 变体）或内存预置表，不宣称没读文件。

约束不变：不改错误返回值、不跳过安全校验、不把非空但不完整字典当作签名成功、不向构建上传安全资源。
