# 洗衣 iOS 204/2404：诊断对照协议

日期：2026-10-02。本轮目标是收集资源选择、访问时序和错误行为的证据；尚未解决 AppKey 空值与统一签名初始化失败。

## 已修正的观察问题

- 缺图观察以前没有校验哨兵的实际命中。现在必须确认 fopen/open 各一次，文件身份及内容各一致两次；创建或自检失败即关闭观察，并清理哨兵。
- 阶段行以前输出累计数。现在输出相邻边界之间的增量，窗口文件行标明开始与结束边界；全窗口总数仍单独保留。
- 沙盒采样自身的读取以前可能混入 SDK 统计。现在仅暂停采样线程，SDK 工作线程继续观察；暂停支持嵌套并在 finally 恢复。
- 目录范围以前会接纳相同前缀的兄弟目录和任意相对文件名。现在只有带目录分隔符的绝对路径前缀匹配才计入目录内记录。相对路径不能由这一记录证明身份。
- 对照生成以前忽略写入失败。现在先校验完整来源，再写入并读回核对；失败不调用 SDK，并删除自己创建的目录。并发检查在创建目录之前拒绝。
- baseline 复制来源的 Info.plist、清单与两张原图，避免自行改造 Bundle 元数据。来源缺失、变体未知或完整性失败不能作为有效基线。
- 沙盒变化以前展示相对路径，并把变化称为派生缓存。现在只报告匿名标签、大小与有限扫描状态；内部摘要不进入报告，变化不归因于 SDK。

正式检查仍要求资源完整性通过；只有诊断入口在完整来源上派生缺图等变体，再使用对照目录调用 SDK。不会修改导入来源。

## 覆盖面的边界

宿主入口自检只证明自身的 fopen/open 跟踪可用，不能证明完整覆盖 SDK、系统库或初始化前的访问。当前静态分析找到的 Foundation 读取用于 embedded.mobileprovision 与 init.config/update.config；ZIP 打开回调另属 C 文件入口。没有建立这些调用到安全图片的读取链路。

跟踪只统计符合条件的读入口。一次打开、身份一致或观察器计算出摘要，均不能单独证明 SDK 随后读取或解析了文件内容。

目录内记录最多 48 条，不是完整文件清单；条目代表打开事件，重复打开会重复记录。除固定资源与配置名外，文件名以匿名标签展示。

沙盒每次最多访问 600 个目录条目、采集 64 个常规文件，每个内容摘要最多读取 64 KiB。大文件只比较大小；没有变化不排除未覆盖文件、同大小内容变化或内存缓存。新进程不会清除持久磁盘状态。

## 静态取证：错误码不是注册表 miss，而是解析器真读了图（本轮）

> **更正（修订 6f5eb65 之后）**：本节标题与下文「证明主图确实被读取并进入了内容校验」的结论**已被真机数据证伪**，保留仅作推理过程记录。仍然成立的部分是「`raw=3/4` 不是注册表 miss」（miss 返回 `1064399xx` 大数）；被推翻的部分是「解析器打开并校验了图片内容」。真机实测 11 条通道全部自检命中，但 `open`/`fopen`/`fd` 全为 0、目标命中 0、目录内 0 —— **图片内容从未被读取**，`raw=4` 只能来自读取内容**之前**的判定。详见「修订 6f5eb65 的设备回报」一节。

`tools/audit_sg_appkey_dispatch.py` 对本地 `build/laundry-ios-analysis` 的 IR 复核，得到一条可排除性证据：

- 原生函数表查找 `CMa02p9LOLd8m1` 在 **miss（找不到处理器）时返回的是大数**：`(group*10000+middle*100+sub)*10000 + 9904/9905/9906`。对 `(1,6,43,0)` 即 `106439904/106439905/106439906`。
- 但真机与两个包装层观测到的底层 `raw` 是 **3 和 4**（AppKey 侧 `4+200=204`；统一签名侧 `switch` 把 `3→2403`、`4→2404`）。
- `(1,6,43,0)` 与 `(1,6,8,0)` 在四个 framework 的原生注册表里都**没有处理器**，说明它们由 AVMP/uvm 字节码实现（虚拟化查询命中）。

**结论（静态证据支持）**：`raw=3/4` 不可能来自「函数表没找到」——miss 会给出 `1064399xx` 而非个位数。因此 `raw` 是 **AVMP 字节码解析器真正打开并校验了图片之后**返回的语义小码：`3`=没找到可用图片数据、`4`=找到但格式/解析失败。这与真机「缺主图→raw 3、主图存在但损坏→raw 4」一致，**证明主图确实被读取并进入了内容校验**，不是纯存在性检查，也不是选路错误。

这把根因从「多种可能」收敛到一条：**候选 5.6 SDK 的 AVMP 图片解析器读到了校园 6.8 图片、按自身格式校验后判为 `raw=4`**。仍属高置信推断，未定位到字节码内的具体校验指令（静态不可见），也未证明代际不兼容是唯一原因。

## 为什么必须换观察面：fopen/open 零命中是方法缺陷（本轮）

AVMP/uvm 宿主函数表（165 项）里**没有 `fopen/open/read/fread/stat`**，字节码读内容只能经 `objc_msgSend` 调 Foundation，探测路径用 `access/lstat/opendir/readdir`。app 级 `fopen/open` interposer 只覆盖自身命名空间、看不到 Foundation 内部读取。两者叠加使 fopen/open **必然零命中**，与 SDK 是否读文件无关。继续加 fopen/open hook 无意义。

## 修订 f615ff0 的设备回报：宿主通道第一轮（证伪上一轮方法）

变体「主图同长度全零」，检查修订 `f615ff0`，自检通过。关键读数：

| 观察项 | 数值 |
| --- | --- |
| 宿主通道调用合计 | 103（NSData 4 / NSString 1 / NSFileManager 18 / access 28 / opendir 52） |
| 目标命中（`yw_1222*.jpg`） | **0，全部通道** |
| 目录内（对照目录） | **0，全部阶段** |
| fopen / open | 0 / 0 |
| 阶段分布 | SDK 初始化 98、签名后 5、**AppKey 阶段 0** |
| 错误码 | 204 / 2404（未变） |

两组独立统计自洽：各通道调用合计 103 = 阶段「目录外」增量合计 103，说明观察器工作正常、数据可信。

**这轮证伪了上一轮的假设。** 上一轮判断「字节码只能经 objc_msgSend 调 Foundation，swizzle 类方法即可覆盖」，覆盖面不够：

1. 只 swizzle 了**类方法**（`+dataWithContentsOfFile:` 等），漏掉实例 `init` 族——字节码经 objc_msgSend 完全可以直接调 `[[NSData alloc] initWithContentsOfFile:]` 绕过类方法。
2. 主动移除了 `stat`/`lstat`（当时担心 `$INODE64`），而 SGMain IR 里 `stat` 有 **36 处调用点**，是覆盖面最大的文件原语。

### 由此确立的两条硬事实

**A. SDK 确实读了对照目录里的主图，但没走任何已覆盖通道。**
目标命中按**文件 basename** 匹配，与目录前缀无关，所以 `/var` 与 `/private/var` 这类规范化差异不能解释零命中。而错误码随那份图的存在性与内容变化（缺图 203 / 全零 204），说明它必然被读到。结论只能是：**它走了本轮之前未覆盖的入口**，缺口是确定的、可闭合的。

**B. C 层 hook 对 SDK 调用有效，`fopen=0` 是真阴性而非观察失效。**
已用 `tools/audit_probe_source_consistency.py` 之外的脚本核对：四个 framework 的每个 slice 都是 `ar` 归档、无 `LC_ID_DYLIB`，即**静态库**。SGMain 的未定义符号在链接期绑定到 app 内我们的定义。旁证是计数关系：

| 原语 | SGMain IR 调用点 | 真机命中 |
| --- | --- | --- |
| `access` | 17 | 28 |
| `opendir` | 6 | 52 |
| `fopen` | 27 | **0** |

真机命中**超过** IR 调用点，差额来自 AVMP 字节码经宿主表调用（宿主表内有 `access`/`opendir`）。既然 `access`/`opendir` 能被抓到，`fopen` 的 0 就是真结果。

**C. `stat` 在真机 arm64 上会绑定到探针定义。**
IR 的 target triple 是 `arm64-apple-ios9.0.0`，且 `stat`/`lstat`/`fopen` 等全部是**纯符号，`$INODE64` 计数为 0**。`$INODE64` 重定向只存在于 x86_64 macOS，不影响真机。核对脚本：`build/laundry-ios-analysis/check_stat_symbol_binding.py`。

## 第二轮覆盖面：补齐三处盲区（本轮已落地，待设备验证）

在 §宿主通道对照轮 的基础上补全，使「零命中」变成可解释的结论而非方法缺陷：

| 盲区 | 本轮补法 |
| --- | --- |
| 实例 `init` 族 | swizzle `-initWithContentsOfFile:`、`-initWithContentsOfFile:options:error:`、`-initWithContentsOfURL:`（NSData 与 NSString） |
| `stat`/`lstat` | 重新拦截；`#undef` 防御 + `PROBE_STAT_SYMBOL` 处理 x86_64 的 `$INODE64` 同代符号，避免 dlsym 取到布局不同的旧 ABI |
| fd 级 | 拦截 `lseek`/`fstat`，用 `fcntl(F_GETPATH)` 反查路径并缓存；`close` 淘汰缓存槽，防 fd 号复用误判 |

同时新增：`NSData/NSString` 的 URL 形态、`-[NSFileManager fileExistsAtPath:isDirectory:]`、`-contentsOfDirectoryAtPath:error:`、`+[NSBundle bundleWithURL:]`、`-pathForResource:ofType:inDirectory:`。

**移除 `read`/`pread` 拦截**：AVMP 宿主表里没有这两个入口（只有 `lseek`/`fstat`/`fcntl`），而它们是全进程最热路径，收益低风险高。fd 级观察由 `lseek`/`fstat` 触发即可，字节内容改由 Foundation swizzle 的返回值做摘要比对。

**每条通道新增 `自检命中` 标注**，这是本轮最重要的判读改进：上一轮零命中无法区分「SDK 没读」与「我没覆盖」，现在自检未命中的通道会在报告里明确标为不可信。自检判据是 `target>0 || scoped>0`——目录类通道（`opendir`、`contentsOfDirectoryAtPath:`）只可能命中 `scoped`，只看 `target` 会让它们永久显示「未命中」。宿主通道自检**不再否决窗口有效性**，否则任一通道的平台差异就会作废整轮真机运行。

## 第二轮判定矩阵（H1 / H2）

静态分析已排除「注册表 miss」（miss 返回 `1064399xx` 大数，观测是 `raw=3/4`），所以 raw=4 必然来自 AVMP 字节码执行。但 **AppKey 阶段宿主通道调用为 0**，字节码跑了却没产生可观察的文件访问。结合五组内容变体（原图/全零/仅头 16 字节/截断/随机）**全部返回 204**，存在两个互斥假设：

| | H1：读得到，但我没覆盖 | H2：根本没读内容 |
| --- | --- | --- |
| 机制 | 经未覆盖的 ObjC selector 或 `stat`/`openat` 读取，解析后拒绝 | `stat` 存在性检查通过（→不是 raw 3），随后在**读内容之前**就失败返回 4，例如程序自身环境/配套数据校验失败 |
| 根因含义 | 6.8 图片喂 5.6 SDK 的**代际不兼容**成立 | 该根因被推翻，指向 **SDK 侧组件缺失** |
| 第二轮预期 | 新增通道对目标出现命中，且 `main-zero` 的内容「不同」>0 | 所有通道仍零命中，但 `stat` 通道对照目录出现命中（存在性检查被观察到） |

**关键区分点**：第二轮若 `stat` 通道命中目标图片而所有**内容型**通道（NSData/NSDataInit/NSString/NSStringInit/NSFileManager/NSFileHandle）仍零命中，即支持 H2——它只检查了存在性，从未读取内容。此时错误码 4 来自读内容之前的校验，继续加文件读取 hook 无意义，应转查 SDK 配套数据/环境要求。

> **判定结果（修订 6f5eb65 真机数据）**：实际结果比 H1/H2 两种预期都更极端——**H2 成立，且 `stat` 通道对目标也是 0 命中**。11 条通道全部自检命中，`stat` 命中 150/151 次但目标命中 0、目录内 0，内容型通道与 `fd` 通道全 0。即 SDK 既没读内容，也没按名 stat 过那两张图，更没访问过对照目录。H1 被排除；H2 的「存在性检查」也不在已覆盖通道内，故矛盾仍未闭合，转入「尚未解开的矛盾」一节的 A/B/C 三个候选解释。

设备步骤沿用 §第一轮（每个变体一个新进程，`baseline` + `main-zero`）。

约束不变：不改错误返回值、不跳过安全校验、不把非空但不完整字典当作签名成功、不向构建上传安全资源。

## 修订 6f5eb65 的设备回报：覆盖面闭合，既有根因假设被证伪

两个变体（`baseline` 与 `main-zero`）均在新进程中运行，检查修订 `6f5eb65`，**11 条宿主通道全部自检命中**。这一点改变了判读性质：上一轮的零命中无法区分「SDK 没读」与「我没覆盖」，本轮的零命中**可以采信**。

### 已确认事实（高置信）

1. **SDK 在整个窗口内没有打开过任何文件的内容。** `open`/`fopen` = 0，且 `fd` 通道（lseek/fstat）= 0。窗口有效性要求 fopen/open 自检各命中一次，故 0 是真阴性。
2. **SDK 从未按名访问过 `yw_1222*.jpg`。** `stat` 命中 150 次，但目标命中 0。目标命中按 basename 匹配、与目录前缀无关，所以 `/var` 与 `/private/var` 的规范化差异不能解释。
3. **SDK 从未访问过 `customBundelPath` 指向的对照目录。** 目录内 = 0，全阶段全通道。探针对该目录的校验发生在 `CampusProbeResourceTraceBeginWithOptions` **之前**（`CampusComponentProbe.m` 的资源校验块在窗口开启前执行），因此窗口内没有探针自身的目录访问噪声。
4. **排除了「字节码直接发原始 syscall 绕过 interpose」。** AVMP 解压后的字节码（139,708 字节）里 `svc`/`brk`/`hvc`/`smc` 模式命中 **0**；原生 IR 的 1611 个内联汇编块里也没有 `svc`/`syscall`。核对脚本 `build/laundry-ios-analysis/audit_avmp_raw_syscall.py`。
5. **文件 I/O 的主体是 AVMP 字节码，不是原生 IR。** 真机命中数与 IR 调用点数的关系：

| 原语 | IR 调用点 | 真机命中 |
| --- | --- | --- |
| `access` | **0** | 28 |
| `opendir` | 8 | 52 |
| `stat` | 37 | 150 |
| `fopen` | 28 | **0** |
| `open` | 3 | **0** |
| `read` | 2 | **0** |

`access` 在原生 IR 里一次都没被调用，真机却有 28 次——只能来自字节码经宿主表调用。反过来，原生 IR 里 28 处 `fopen` 调用点在真机一次都没执行。

### 既有根因假设被证伪

把八组对照按「主图是否存在」重排：

| 主图 `yw_1222.jpg` | 内容 | 错误码 |
| --- | --- | --- |
| 存在 | 真实校园图片 | 204 |
| 存在 | 同长度全零 | 204 |
| 存在 | 同长度随机字节 | 204 |
| 存在 | 截断为一半 | 204 |
| 存在 | 仅保留前 16 字节 | 204 |
| 存在 | （mwua 缺失，主图保留） | 204 |
| **缺失** | — | **203** |
| **缺失** | （两图都缺） | **203** |

分界线是**文件存在性**，不是内容。五种完全不同的字节内容给出同一个 204。

结合事实 1–3（内容从未被读取、对照目录从未被访问），此前记录的根因推断——「校园 6.8 图片喂公开百川 5.6 SDK，图片**内容**代际不兼容」——**被证伪**。图片内容根本没有进入任何解析器，204 不可能是内容校验的结果。

### 尚未解开的矛盾（下一轮要回答的唯一问题）

事实 3（SDK 从未访问对照目录）与八组对照（错误码对对照目录里主图的存在性敏感）**互相矛盾**。一个文件的存在性影响了错误码，却没有任何已覆盖通道碰过它。

可能的解释，按可检验性排序：

| 假设 | 内容 | 如何检验 |
| --- | --- | --- |
| **A. 走了仍未覆盖的通道** | 剩余未拦截入口：`readdir`、`openat`、`getattrlist`、`mmap`；Foundation 的 `enumeratorAtPath:`、`subpathsAtPath:`、`contentsOfDirectoryAtURL:...`、`dataWithContentsOfURL:options:error:`、`URLForResource:withExtension:`、`contentsEqualAtPath:andPath:` | 本轮已加「目录外访问归类」，可先定位 SDK 在哪找图，再决定是否补这些入口 |
| **B. 存在性信号不来自文件系统** | 203/204 的差异由对照目录的其它属性引起（例如目录内文件数量、Info.plist 内容、Bundle 结构），SDK 通过 `customBundelPath` 之外的途径感知 | 需要设计只改文件数量、不改内容的对照 |
| **C. `customBundelPath` 未被 5.6 SDK 消费** | SDK 忽略自定义路径、只看 mainBundle；203/204 来自别处 | 「目录外访问归类」若显示大量 app 包内访问即支持此说 |

### 本轮新增仪器：目录外访问归类

上一轮那 254 次目录外访问只计数、不记名，是完全的盲区。本轮补上三条报告行（`ProbeRecordOutsideLocked`）：

| 报告行 | 内容 | 隐私边界 |
| --- | --- | --- |
| `目录外访问归类` | 合计 + 应用包内 / 临时目录 / 用户目录 / 系统目录 / 其它 | 只给粗粒度类别计数，不含任何路径 |
| `目录外访问扩展名` | 图片 / plist / 数据库 / 配置 / 无扩展名 / 其它 | 只给后缀类别，不含文件名 |
| `目录外安全资源命名` | 匹配 `yw_*` / `mwua` / `jaq` 命名域的 basename（去重、上限 8 个） | **故意不按 `.jpg` 扩展名匹配**——那样会把窗口内访问到的用户照片名（如相册 `IMG_1234.JPG`）写进报告，违反「报告不得泄露用户数据」 |

`yw_1222.jpg` 与 `yw_1222_mwua.jpg` 都由 `yw_` 前缀覆盖，收窄不影响调查目标。

同时修掉一个会污染真机数据的缺陷：`ProbeOutside` 原先只在窗口开启时清零，**自检阶段产生的目录外访问会漏进报告**，把探针自己的 I/O 冒充成 SDK 的行为。现已与 `ProbeHost` 一起清零。

新增不变量断言（已用 Python 模拟验证）：两组分类各自的类别之和必须等于合计；各通道「目录外」之和必须等于归类合计（两条计数走不同代码路径，相等才说明接线没漏）。

## 第三次 CI 失败与修复（桩测试断言，非编译错误）

`75a01b3` 编译通过、桩测试开始运行，但在 `CheckDiagnosticTrace` 的断言「两图缺失时必须校验哨兵的两个入口」处 `exit(1)`，配合构建脚本的 `set -euo pipefail` 终止 Step 3。

根因是 `bc59d50` 重写时把哨兵文件的准备顺序弄反了：

| 版本 | 顺序 | 结果 |
| --- | --- | --- |
| `f615ff0`（曾通过） | `writeToFile:` → `stat()` | 文件已存在，取到 dev/ino |
| `bc59d50`–`75a01b3` | `stat()` → `writeToFile:` | 文件尚不存在，stat 必然失败 → `return NO` |

该分支只在**参考资源缺失**时进入（`needCanary`）。真机 `main-zero` 变体两图俱在（主图被替换为同长度全零，文件仍在），走不到这里，所以两轮真机运行都没暴露它，只有桩测试的「两图缺失」场景能触发。

同时修掉 `CheckHostChannelTrace` 里三处**从未被运行过**的断言（`bc59d50` 编译失败、`75a01b3` 在它之前中止，因此该测试一次都没执行过）：

1. `stat`/`fd` 通道断言 `target >= 2`，改为以 `selfChecked` 门控且只要求 `>= 1`。是否命中取决于 `stat`/`lstat`/`fstat`/`lseek` 的 C 符号在本平台能否绑定到探针定义，属平台行为而非探针逻辑；`fd` 通道还需 `lseek` 与 `fstat` 都命中才有 2。
2. `endTarget >= 10` 改为 `>= 9`。按测试体逐次核对，平台无关的必然命中是 9 次（NSData 1、NSDataInit 2、NSString 1、NSStringInit 1、NSFileManager 1、NSFileHandle 1、NSBundle 1、access 1）；原先的 10 把通过与否押在 stat/fd 命中上。
3. `containsString:@"目录内 1"` 这类精确字符串匹配改为解析数值后 `>= 1`。阶段行是各通道汇总，Foundation 内部若对目录外路径多产生一次调用就会变成 2，精确匹配会因此失败。

`audit_probe_source_consistency.py` 新增哨兵顺序断言，并已双向验证：注入「stat 在 write 之前」时精确报错，恢复后通过。
