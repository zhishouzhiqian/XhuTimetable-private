# 西瓜课表 iOS 校园整合测试

本工作流把西瓜课表的 Compose 静态框架、现有原生授权/扫码页面和校园查询客户端编入启动库。运行时由已核对的校园 5.7.2 原二进制承载，复用其 SDK 6.8.260603 与原配资源。课表与安卓共用 `LaundryContent`、`LaundryViewModel` 和导航入口。

目前支持本人授权登录、扫码查询设备状态和开放程序、运行订单及详情核验、历史订单第一页、手动刷新及页面原有轮询。每次请求重新签名。本人登录成功后将 sid/uid 保存在独立 Keychain 条目，绑定原 AppKey、UTDID、TTID 与返回设备 ID 的 SHA256 摘要；重新启动只能恢复同一设备上下文的候选会话，并查询本人资料验证后才允许订单与付款操作。服务端报告失效或主动退出时删除会话条目，付款意图保留。会话保存失败会明确提示，不冒充保存成功；真实 Keychain 与进程重启仍需真机验证。不查询未通过的楼栋和常用设备入口。

付款版本沿用安卓共享页面：每次预览重查机器和程序，再向 `RENDER_ORDER` 查询应付金额。点击确认后重新报价并比较金额；服务端返回唯一订单编号后，先写入独立 Keychain 付款意图并回读核对，再至多创建一次。收银台、创建结果与恢复详情均核对原订单身份及整数分金额；微信返回只触发服务端重新查询，不代表付款完成。

付款意图绑定当前账号，保存订单编号、机器、程序、整数分金额及已验证的收银台编号，登录令牌由独立会话条目保存。创建超时或响应不一致时保留意图，重新启动登录后查询本人历史订单和详情恢复，不再次创建；第一页未找到时保持“结果待确认”。只在用户确认且服务端重新返回 `SUCCESS/CLOSE` 时清理。Keychain 存取失败或账号不符时拒绝下单，不使用偏好设置或临时内存替代。首次保留槽位使用 `SecItemAdd` 原子新增，已有意图不能被覆盖。

报价核对失败时显示本地固定检查点：设备字段、报价 resNo、businessType、serviceItemDTOList 或 serviceItemId 的缺失、结构异常或不一致；不显示服务端值。真机 v14 已确认五个程序的 key 均被原付款模型的编号字符白名单误拒绝，导致 QUOTE_RENDER_BODY，报价尚未发送。程序 key/serviceItemId 改为与设备页面一致的非空有界原始字符串，允许标点，不裁剪、转换或替换；控制字符、超过 128 字符及包含 & 的标识仍拒绝。报价与所选程序精确比较，机器、订单和收银台编号继续使用既有编号契约，整数金额与正文签名核对不变。回归覆盖含标点的程序发现、报价、创建正文与表单编码；真实报价和付款仍待整合版真机验证。

报价、序列、创建、收银台、支付渠道契约移植自仓库安卓实现 `LaundryOrderProtocol` / `LaundryPaymentProtocol`，使用同一 MTOP 服务。iOS 原配 SDK 签名仍每次重新生成。所有付款目的固定在 `acs.m.taobao.com`，关闭 Cookie、跳转和应用层自动重试；不会在诊断或应用启动时自动创建订单。微信只使用现有官方小程序重定向方式，缺少可用渠道时保留订单。

程序列表价格仍只展示服务器明确提供的 `priceYuan`；报价计算按已核对的安卓协议将 `price`、`totalAmount`、`discountAmount` 与 `actualPayAmount` 作为整数分，拒绝小数、布尔、负数、溢出和金额不一致。剩余时间只在本人订单详情确认支付/履约状态，且运行列表提供有效秒数时显示；倒计时归零不能当作洗衣完成。

## 构建与本地合成

在分支 `fix/ios-campus-sdk-init` 手动运行 Codemagic 的「西瓜课表 iOS 校园整合测试（原配载体）」；私有依赖仍使用既有 `private_maven` 变量组。工作流先运行共享 iOS 测试、原生桩测试和模型测试，再编译真正的课表框架、跨语言客户端与原生页面。Compose 的正式 `syncComposeResourcesForIos` 任务收集主模块及依赖资源，缺失资源则拒绝打包。

下载 `XhuCampusTimetableHost.zip`，在本机运行：

```text
python tools/prepare_campus_timetable_host.py --ipa <原天猫校园_5.7.2.ipa> --artifact <XhuCampusTimetableHost.zip> --output <新的整合测试.ipa>
```

输入文件不修改，已有输出不覆盖。合成后递归重签并用已验证的 LiveContainer 安装方式运行。首次启动应展示课表页面，从课表既有洗衣入口授权登录、扫码、核对报价后本人确认下单付款。付款版本标记为 `xhu-campus-timetable-host:2`，打包器拒绝旧的只读整合库。

## 验收与边界

本机 Windows 只能运行 Python 打包测试和脚本静态检查；原生编译、共享 iOS 测试交给 macOS 构建，最终启动和校园查询需要真机验收。此包仍保留校园原 SDK 所需的 Bundle ID 与原载体，应用数据与原校园容器环境相关；不算解决将厂商 SDK 搬到普通独立课表 IPA 的问题。正常课表构建不安装此实验客户端，不宣称洗衣已可用。

课表其它功能、推送、Widget 与校园载体的共存尚需验证；本宿主只接课表主页面与洗衣能力，不替代正常发布宿主中的推送/Widget 生命周期。

## 整合库链接

整合产物是动态库，默认公开所有全局符号会把 Kotlin 平台缓存中的未调用包装器也作为保留根。使用 `exports.list` 只公开外部启动入口和版本标记，配合 `-dead_strip` 清理未调用的代码。课表控制器通过 Swift 的 C 入口直接调用，避免依赖字符串反射来保留启动路径。真实可达依赖仍须在链接时解析，不使用缺失 API 的替身或动态查找来绕过失败。

`test_campus_timetable_linker.sh` 在 macOS 检查三种情况：默认导出重现缺失包装器、限定导出后能实际调用启动工厂、缺失符号成为真实依赖时仍拒绝链接。整合库最终导出也逐项核对，链接图与导入清单供进一步定位。

合成包的 `Info.plist` 必须保留课表宿主要求的布尔项 `CADisableMinimumFrameDurationOnPhone = true`。原校园主应用没有此项，不能仅保留原包配置；缺失会触发 Compose 的严格启动检查。打包测试同时检查原载体为 false 时的修正结果和正常课表宿主配置。[Compose 官方启动要求](https://kotlinlang.org/docs/multiplatform/compose-swiftui-integration.html)

初始化失败时，共享页面显示原检查流程的固定脱敏阶段（资源、SDK、请求一致性、匿名配置、设备注册和返回 ID 复用）。普通异常正文仍不展示。原生桩测试检查失败阶段、同实例重试、就绪缓存及未登录状态；不会加载厂商 SDK 或发送请求。

## 付款验证

构建时运行付款协议与状态机桩测试：固定 POST 范围、金额与订单对照、微信嵌套编码、变价拒绝、存储前置、重复点击、创建超时与重新启动恢复、账号隔离，以及只有 SUCCESS/CLOSE 能清理意图。测试不调用真实支付、SDK 或 Keychain。仍须在真机验证 LiveContainer 的 Keychain 支持、真实报价、本人确认创建、微信跳转及服务端终态；编译或桩测试成功不等同于这些实测通过。

## 已验证载体的资源精简

用户已确认 v5 整合版验收通过。后续精简使用 `tools/slim_campus_timetable_host.py --ipa <已验证整合 IPA> --output <新精简 IPA> --report <新报告.json>`，不覆盖输入或已有输出。仅按明确名单清理原校园 AI、首页、消息、商城、地图、广告素材、页面动画/音效、业务数据库及通知/实时活动扩展；不泛化删除未知 Bundle 或配置。所有保留文件（包括 Info.plist）逐字节核对，并再次校验动态加载依赖闭包、原配安全图片及整合库清单。

原校园业务与安全 SDK 静态链接在同一个主程序中，且主程序直接加载多个广告等动态库；删除素材不等同于移除这些代码，也不证明原二进制加载期活动被关闭。主程序、全部 Frameworks、Compose 资源、图标及 SDK/登录默认配置保留。当前工具不改 Mach-O 代码、符号表、加载命令、Bundle ID 或 Keychain 配置，不宣称已得到独立可发布的最小 SDK 载体。

精简包仍需在相同重签/LiveContainer 环境验证启动、校园会话跨进程恢复、扫码/切换程序/报价、本人确认下单、微信跳转返回和订单状态。原验证包保留作对照；安装时替换同一整合应用以保留容器数据。文件一致性与离线测试不能代替这轮真实功能验收。
