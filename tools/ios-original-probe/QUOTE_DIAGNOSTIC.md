# 诊断版本 14：本地设备转换与洗衣报价核对

在 `fix/ios-campus-sdk-init` 手动构建「iOS 校园原配本地诊断库（未签名）」，工作流 `ios-campus-original-probe`。该工作流只构建 Objective-C 诊断库，不运行 Gradle/Compose。

下载新的 `CampusOriginalProbe.dylib` 后，在原校园 IPA 的独立副本上运行 `prepare_campus_original_probe.py`，递归重签并安装。原始 IPA、课表整合 IPA 与原容器不覆盖。先点击联网综合检查，全部通过后在机器输入框填写这次报错机器的官方二维码链接或机器编号，再执行本人登录综合检查。

设备详情身份通过后，先逐个核对候选程序的本地设备字段类型、付款标识格式、设备/计费类型、campusAreaId 整数、程序匹配数量、价格格式与 Render 正文转换。转换通过后才进入签名及 POST 构造；固定错误代码分开报告，不再将所有本地异常合并为同一条信息。针对本机候选程序串行执行至多五次固定报价请求。复制完整报告，其中逐项包含 `response` 的类型、`resNo/isvResNo/deviceId` 与输入的对照、业务类型、程序数组结构与身份、三个金额字段的整数分校验、总额减优惠等于应付的独立核对。所有字段值、设备标识、金额和账号信息都不输出。

真机 v13 报告显示五个程序全部在报价发送之前失败；因此尚不能认定为服务端报价字段不一致。设备页面与付款模型的标识格式检查确有不同，但没有对应真机字段检查结果前不能将其认定为本次根因，也不能直接放宽付款验收。用户要求原因确认后再构建课表整合版，当前继续使用轻量诊断。

后续 v14 真机报告已确认：五个程序 key 的付款格式均被拒绝，机器与设备 ID、计费类型、价格整数及唯一程序匹配均通过，转换失败点为 QUOTE_RENDER_BODY。根因是程序原字符串误用了订单编号的字符白名单。已单独修复程序标识契约并新增回归；下一步恢复 `ios-campus-timetable-host` 整合构建，同时验证会话保存，无需继续重复轻量诊断来定位这个已确认的根因。

当前整合版截图只证明报价检查拒绝了结果，尚未确认具体响应差异。此诊断复用整合版报价模型与签名正文；出现类型或身份不一致时不放宽验收。编译宏 `CAMPUS_QUOTE_DIAGNOSTIC` 仅增加 Render API，订单编号、创建及收银台/付款 API 不在诊断请求白名单。原生测试验证这一边界，且不访问 SDK 或网络。诊断会话仍仅在本进程内存；整合版会话保存变更由后续整合工作流及真机验证。
